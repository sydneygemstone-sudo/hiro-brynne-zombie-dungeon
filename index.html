Playability Review

It works. It is not “great fun” yet.

The strongest part is that there is a real beginning → challenge → boss → treasure → escape loop. The weakest part is that most moments still ask the player to do only one thing: walk forward and fight.

Combat feedback6/10
Exploration & room variety4.5/10
Meaningful choices / strategy3/10
Progression / upgrades3.5/10
Replayability2.5/10
Two-player classroom excitement6.5/10

What is already fun

  • Hitting zombies gives immediate visual/audio feedback.
  • Finding a sword noticeably changes combat power.
  • The locked crypt + Zombie King gives the run a visible climax.
  • Escaping with the treasure gives the game a proper ending.
  • Two iPads in the same dungeon naturally creates social excitement.

What still feels flat

  • Fixed map and mostly fixed encounters.
  • Very few “fight, flee, risk, save, spend” decisions.
  • No build choices or upgrades after success.
  • Co-op is shared space, but not yet true cooperative mechanics.
  • Rooms look different only slightly; they do not play very differently.
Why it did not suddenly become amazing

The missing layer was game design, not code.

Was Brynne’s brief too vague?

Partly — but that is normal for a child designer. Brynne gave useful playtest feedback: the maze felt too short, there were too few things to interact with, movement/facing felt wrong, pacing was too fast, and the dungeon needed darker lighting plus stronger music, zombie and environment sounds. She also identified what was already enjoyable: zombie combat, hit feedback and the Victory moment.

That is good user feedback. What it did not yet specify was the deeper rule system that creates replayable fun.

The bigger reason

The original classroom brief explicitly optimised for a playable MVP in roughly ten minutes: multiplayer first, then movement, zombie pursuit, combat, victory, items, and only then visual detail. AI therefore did the rational engineering thing: it completed a checklist.

Adding a key, a door and a boss improves content, but does not automatically improve decision density. A fun game needs repeated choices, changing pressure, rewards, surprises and reasons to replay.

Child’s job

Say what they imagine, play it, notice feelings, explain what they want changed.

Teacher’s job

Turn “make it scarier / longer / more fun” into testable mechanics and better questions.

AI’s job

Implement, test and iterate quickly — but not pretend that feature completion equals fun.

Development Log

From idea → prototype → feedback → iteration

The log is deliberately transparent: students and parents can see that software is not “one magic prompt”. It is a cycle of specification, building, testing, criticism and revision.

10:52 · Classroom MVP brief

Define the minimum playable experience

First-person Minecraft-style dungeon, two real players on iPads over LAN, zombie pursuit, combat, sword, bandages, treasure and escape. The constraint was explicit: functionality before visual polish.

Morning · First playable build

Turn the idea into a running system

Three.js rendering, Socket.IO state sync, touch controls, zombie AI, health/damage, item pickup and a win/lose loop were assembled into a classroom-playable prototype.

Student playtest · Brynne feedback

The first version was challenged, not defended

Brynne identified a short maze, too few interactables, reversed character/zombie facing, movement that felt too fast, and a need for darker atmosphere plus stronger music and environment/zombie audio. Combat, red hit feedback and the Victory moment were worth keeping.

Iteration · V2

Improve pacing and content density

The dungeon became larger, item interactions and audio feedback were expanded, lighting/fog were strengthened, and movement/facing issues were targeted.

22:00+ · V2.1 standalone release

Key → crypt gate → Zombie King → treasure → escape

A complete single-player browser version was added while preserving the classroom LAN co-op architecture. The release was smoke-tested, full quest logic was verified, committed to GitHub and deployed to GitHub Pages.

Who did what?

AI-assisted does not mean student-free.

🧒

Students

Theme and desired experience, gameplay reactions, identifying bugs, saying what felt fun or boring, and deciding what should change next.

🧑‍🏫

Teacher

Time/scope constraints, questioning, translating feedback into specifications, choosing what to prioritise, quality assurance and deciding when the prototype is ready to test.

🤖

AI tools

Fast code implementation, repetitive asset construction, networking boilerplate, debugging assistance, build/test automation and rapid iteration from concrete requirements.

Learning Value

The important skill is not “AI made a game”.

1 · Clear communication

Students see that “make it better” produces generic changes, while specific observations create specific improvements.

2 · Iterative design

A first version is evidence, not a final answer. Playtesting converts opinion into data for the next version.

3 · Systems thinking

Movement speed, enemy speed, health, damage, rewards and map layout interact. Changing one value changes the whole experience.

4 · Debugging

“The zombie walks backwards” becomes a coordinate/orientation problem that can be reproduced, fixed and verified.

5 · Real software architecture

The classroom version synchronises multiple devices over Socket.IO, while the public version simulates the same event interface locally in one browser.

6 · Critical judgement

Students learn not to accept AI output just because it runs. They are expected to say when the result is boring, confusing or wrong.

Next Design Challenge

Five questions that would make V3 genuinely more fun

The next lesson should spend less time asking AI to “add features” and more time answering these design questions first.

What decision should the player make every 20–30 seconds?
Fight, sneak, spend a bandage, take a risky shortcut, save a key, rescue a teammate?
What changes after each success?
Roguelike three-choice upgrades, new weapon traits, more dangerous enemy combinations?
Why is two-player mode better than playing alone?
Different roles, revive mechanics, split switches, shared resources, combo attacks?
What surprise makes a second run different?
Random rooms, shuffled loot, optional treasure rooms, elite enemies, changing boss modifiers?
What skill should the Zombie King test?
Dodging, teamwork, timing, resource preparation — not just a larger HP number.

已经有趣的东西

  • 打中僵尸以后有非常直接的声音和视觉反馈。
  • 捡到剑以后战斗能力真的会发生变化。
  • “钥匙 + 墓室门 + Zombie King”让过程终于有了高潮。
  • 拿到宝藏还必须逃回来，结尾是完整的。
  • 两台 iPad 同屏不同角色，本身就会带来社交乐趣。

现在仍然平的地方

  • 地图、怪物、奖励基本固定。
  • 几乎没有“打还是跑、冒险还是保守、现在用不用资源”的选择。
  • 成功之后没有三选一升级或 Build 成长。
  • 双人现在是“在一起玩”，还不是“必须合作才能解决”。
  • 不同房间看起来有差别，但玩法差别还不够大。
为什么没有一下变得很好玩

真正缺的不是代码，而是“游戏设计”这一层。

是不是 Brynne 没讲清楚？

有一部分是，但这对孩子来说非常正常。 Brynne 的试玩反馈其实已经很好：她指出迷宫太短、可互动的东西少、人物和僵尸方向不对、移动节奏太快，还希望更黑、更有音乐、僵尸声和环境声；同时她也明确保留了自己觉得好玩的部分——打僵尸、受击红闪、Victory。

这些是很好的“用户反馈”。只是它还没有继续变成“什么规则会让第二局、第三局仍然想玩”的游戏机制。

更大的原因是什么？

第一版原始任务明确要求大约 10 分钟内先做出课堂 MVP，而且优先级就是：双人联网 → 移动/视角 → 僵尸追击 → 战斗 → 宝藏/胜利 → 武器绷带 → 最后才是美术。因此 AI 很自然地完成了一个“功能清单”。

后面加钥匙、门和 Boss，是增加了内容，却没有自动增加决策密度。真正好玩的游戏，需要持续选择、压力变化、奖励、惊喜，以及再来一局的理由。

孩子负责什么

提出想象、亲自试玩、说出哪里爽/哪里无聊/哪里不对，并决定下一版想改变什么。

老师负责什么

把“更恐怖、更长、更好玩”追问成可以实现和验收的规则，而不是让孩子自己写完整游戏策划书。

AI负责什么

快速实现、测试、修 bug、根据明确要求迭代；但不能把“功能都做完了”冒充成“游戏一定好玩”。

教学意义

真正要学的不是“AI帮我做了一个游戏”。

1 · 清楚表达

孩子会看到：“弄好一点”通常只会得到泛泛的改动；具体观察才能换来具体改进。

2 · 迭代设计

第一版不是答案，而是一份证据。试玩之后，主观感觉才可以变成下一版的需求。

3 · 系统思维

玩家速度、怪物速度、血量、伤害、奖励和地图并不是独立数字；改变一个，就会改变整体体验。

4 · Debug 思维

“僵尸倒着走”会被翻译成坐标系/朝向问题：复现 → 找原因 → 修复 → 验证。

5 · 真实软件架构

课堂版通过 Socket.IO 同步多台设备；公开版则在单浏览器内模拟同样的事件接口，让一套前端同时支持两种运行方式。

6 · 批判 AI

代码能跑不等于结果就好。孩子被鼓励直接告诉 AI：“这个不好玩”“这个不对”“我要改”。

下一版设计挑战

V3 先回答这 5 个问题，再让 AI 写代码

下一节课应该少花时间让 AI“再加几个东西”，先把好玩这件事说具体。

玩家每 20–30 秒应该做一次什么选择？
打还是跑？现在用绷带吗？走安全路还是冒险拿奖励？救不救队友？
每次成功以后，玩家应该变强在哪里？
Roguelike 三选一、武器词条、技能变化，还是新的战斗方式？
为什么两个人一起玩要明显比一个人更好玩？
不同职业、复活、双机关、共享资源、连携技能？
第二局为什么会和第一局不一样？
随机房间、随机掉落、可选宝藏房、精英怪、Boss 随机特性？
Zombie King 到底要考玩家什么能力？
走位、配合、时机还是资源准备，而不是只把 HP 调大。
